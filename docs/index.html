A small, honest benchmark · November 2026

Three coding models,
two harnesses, five tasks

Inkling 2 Mini and Qwen3.8 27B running locally on a MacBook Pro, against Claude Haiku 5.5 on Amazon Bedrock. Each model builds the same web apps inside Claude Code and inside a deliberately plain neutral agent loop, and every result is checked by an autograder in a headless browser.

Use → / ←, or scroll · Code and data: github.com/ipattis/inkling-2-mini-play

The short version

  • Correctness didn't separate the models. 28 of 30 runs passed every autograder check. The two misses were real bugs, both in Qwen's neutral-loop output.
  • Speed did. To finish all five tasks in Claude Code, Inkling 2 Mini took of Haiku's time and Qwen3.8 27B took . This compares local generation on one Mac against Anthropic's servers on Bedrock.
  • The harness mattered, but not the way I expected. The neutral loop made Haiku as long and Qwen . It made Inkling as long, that is, slower. Claude Code's overhead cost Haiku the most in relative terms; it didn't hand Haiku an advantage.
  • The grader needed fixing too. Real outputs exposed 5 false negatives in my autograder, all from reasonable readings of the spec. Each fix shipped with a positive and a negative control, and every run was regraded.

How a run works

  1. 1Task promptthe same text for every model; some tasks also start from seeded files
  2. 2HarnessClaude Code (claude -p) or the neutral loop
  3. 3Modelllama.cpp on this Mac, or Bedrock
  4. 4Files on diskindex.html, styles.css, app.js…
  5. 5Autograderheadless Chromium, one check per stated requirement

What gets measured

  • Autograder score: checks passed out of 15–22 per task
  • Time to complete: wall clock from launch to exit
  • Cost: Haiku at list price; $0 API spend for local runs (hardware and power not counted)
  • Tokens, API calls, tool errors, tok/s, and time to first token

Scheduling

  • A batch is a list of jobs: task × harness × repeat.
  • Within a job, Haiku runs alongside the first local model.
  • Only one local model uses the GPU at a time, so they don't slow each other down by sharing memory bandwidth.
  • A run is stopped after 45 minutes.

A live dashboard (npm start) shows every run as it happens: a metrics panel above the page being built.

Generation speed (median tok/s across tasks, Claude Code harness)

Local decoding is bound by memory bandwidth: a 27B dense model at 8-bit reads about 29 GB of weights per token. Inkling's mixture of experts touches far fewer weights per token, so it runs about 2× faster than Qwen on the same chip.

Five tasks, each a different skill

Every task is a single-page app built from three files, with no frameworks, CDNs or build step. The prompts state each requirement explicitly, so each one can be checked mechanically.

The autograder, and how it was kept honest

How it grades

  • It serves each output folder and drives it in headless Chromium, blocking every non-local request.
  • Each stated requirement gets one check. The checks are written so that one defect fails one check, not several.
  • Timers run on Playwright's fake clock, so "60 seconds" or a full 25-minute session take milliseconds and are exact.
  • Expected answers come from the task's own data. The data explorer's expected sort orders, for example, are computed from data.json.

Negative controls

Each grader is run against a known-good reference app, and against copies of it with one deliberate defect each. Every case must fail exactly the checks it should:

  • Spreadsheet: uses eval · floating-point noise · no #CIRC! · Clear keeps formulas
  • Data explorer: orders sorted as text · ties by id descending · hash not restored · totals for the current page only
  • Bug fix: the untouched seed must fail exactly the 7 bug checks
  • Markdown: raw HTML rendered · javascript: links allowed · no autosave

Real outputs still found 5 false negatives

Each one came from a reasonable reading of the spec, and each fix shipped with a positive control (the model's real pattern must pass) and a negative control (the real defect must still fail):

  1. a session counter labeled only by aria-label
  2. empty spreadsheet cells shown as “0”
  3. sort buttons inside the <th>, the accessible pattern
  4. a table that starts out sorted, so the first click flips it
  5. “No results” shown next to a “Showing 0–0 of 0” line

Every run in this deck was regraded with the final grader.

Neutral loop design

The whole system prompt

You are an autonomous software engineer working in a project directory.
Use the provided tools to inspect, create and edit files; paths are relative to the project directory.
Work until the task is fully complete, then reply with a one-line summary and stop calling tools.

The loop

  1. Send the conversation and the tools to the model, streaming.
  2. No tool calls? The model is done; record its summary.
  3. Otherwise run each tool call, validating its arguments and keeping it inside the run folder.
  4. Append the results and repeat, up to 60 turns and 32K output tokens per response.
  5. A call cut off at the output limit isn't run; the model is told to split large writes.
  6. Network errors, 429s and 5xx responses are retried up to 3 times with backoff.

Five tools

list_filesrecursive listing, up to 200 entries
read_filethe file's text, truncated at 100K characters
write_filecreate or overwrite a file
edit_filereplace one exact match; fails if there are 0 or more than 1
check_javascriptnode --check, a syntax check only

Each model through its native API

LocalOpenAI-style chat completions on llama-server, using each chat template's own tool-call format. Reasoning goes back as reasoning_content; KV-cache reuse is automatic.
HaikuMessages API on Bedrock, effort: medium and adaptive thinking. Thinking blocks go back unchanged; cache breakpoints sit on the system prompt and the newest message.

It emits the same event stream as Claude Code's --output-format stream-json, so time, tokens and cost are measured by identical code in both harnesses. The whole loop is about 300 lines: harness/neutral-agent.mjs.

Keeping it fair

Effort parity, verified

A capture of real requests showed Claude Code sending effort: high to models it doesn't recognise and medium to Haiku 5.5. llama-server honors the per-request value. So the Claude Code runs pin --effort medium, and the capture confirms all three models now get medium.

Model-card sampling

llama-server is started with each model card's recommended sampling, so both harnesses get it. Its own defaults (temperature 0.8, top_k 40, min_p 0.05) differ from both cards.

One local model at a time

Both local models share one GPU and its memory bandwidth, so they never run at the same time. Haiku runs remotely, alongside the first local model.

Same inputs

The same prompt, seed files and grader for everyone. Within a harness every model gets the same tools and limits.

Integration fixes for the local models

Fixes needed to get Claude Code working with the local models:

  • Bash and TodoWrite added to the tool list, because llama.cpp's tool grammar returns a 500 on unknown tool names
  • Qwen's chat template patched to accept mid-conversation system messages
  • cloud-provider settings removed so requests go to the local server

Regraded at the end

The grader changed during the study (see the 5 false negatives). Every archived run was regraded with the final version, so all the numbers come from one grader.

Results: the harness effect

  • Haiku and Qwen did less work in the neutral loop. Haiku went from 39 to 17 API calls and from 89k to 49k output tokens; Qwen went from 52 to 32 calls and from 68k to 42k tokens.
  • Inkling did more. It made fewer calls (72 vs 91) but wrote 98k output tokens instead of 80k, about twice as much on the Pomodoro and data-explorer tasks, mostly extra polishing passes.
  • A small prompt speeds up the first token. Median time to first token fell from 16.2 s to 3.9 s for Inkling and from 23.8 s to 6.3 s for Qwen. Haiku went from 3.9 s to 3.2 s.

What they built

Caveats

One run per cell

Model output varies from run to run. The timing and harness differences are suggestive, not settled; Inkling's neutral-loop slowdown in particular could be noise. Repeats would settle it.

Saturated tasks

Single-page apps from explicit specs turned out to be well within all three models' reach. Separating them on quality needs bigger, multi-file tasks or work inside an existing codebase.

Hardware, not just models

Local times reflect one M4 Max. Haiku's times reflect Anthropic's servers on Bedrock. Local decoding is bound by memory bandwidth, so hardware with more bandwidth would run the same local models faster.

Cost isn't the full cost

“$0” is API spend only. The Mac, its power, and the hour-plus of compute per local run aren't priced in.

No test execution

Neither harness let a model run arbitrary code; node --check was the most it could run. Qwen spent much of one run building a test harness it wasn't allowed to execute.

Grader iteration

The grader was corrected after seeing real outputs. Each fix was justified from the spec and paired with a control, and everything was regraded. Still, a grader written by one person carries that person's reading of the spec.

Reproduce it

# model weights, SHA-256 checked (needs llama.cpp b12633+ in ~/.local/llama.cpp)
scripts/fetch-models.sh
npm install

# live dashboard: http://localhost:4100
npm start

# grader negative controls (all tasks)
node grader/selftest.mjs

# regrade everything, then rebuild this deck's data
node grader/regrade.mjs
node scripts/export-pages.mjs
